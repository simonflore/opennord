The most useful work now is on the product: the screens players use, more
instruments supported end to end, and testing with real instruments and files.

## What helps most

1. **Test with your own Nord.** Run **Check my Nord** and share the result, or
   [open an issue](https://github.com/simonflore/opennord/issues/new) for a file
   that doesn't open correctly. Owners of models marked "ready to test" help
   most.
2. **Product and UI.** The Library, the program views, the sample workshop and
   the device screen.
3. **More instruments.** Readers for models that are recognised but not yet
   read in full. See [Supported instruments](/docs/reference/instruments/).
4. **Docs.** If something here is wrong or missing, fix the page. Every page has
   an "Edit page" link at the bottom.

## Ground rules

- **Share players' own work only.** Never add a path that shares or redistributes
  Nord's factory sounds or sample libraries. See
  [Legal](/docs/reference/legal/).
- **Keep hardware optional.** Everything that can work from a file must.
- **Small, tested steps.** A small pull request with a test beats a large
  speculative one.
- **Update the docs in the same pull request.** If a change is something a
  player would notice, the page that describes it changes too, and the
  [changelog](/docs/reference/changelog/) gets a line.

## License, sign-off and grant

- Contributions are licensed under the project's **AGPL-3.0-or-later**.
  Don't paste in code from projects with an incompatible license.
- **Sign off your commits** (`git commit -s`), certifying under the
  [Developer Certificate of Origin](https://developercertificate.org/) that you
  have the right to submit the patch.
- You keep the copyright to your contribution, and grant the maintainers the
  right to license it under the project's license and under other terms they
  may choose for the project.
