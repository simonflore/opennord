# Spec: signed, installable, versioned desktop releases

**Date:** 2026-10-11
**Status:** Draft — awaiting review
**Scope:** spec 1 of 3 towards a self-updating desktop app. Spec 2 is auto-update,
spec 3 is shell hardening (Electron upgrade, sandbox, single-instance, unplug
handling). Neither is designed here.

---

## Goal

A Nord owner downloads OpenNord for macOS or Windows from the public repo's
Releases page, installs it like any other app, and it opens. Today they get an
unsigned `.app` folder (macOS) or a zip (Windows), both at version `0.0.1`.

This spec makes the artifacts trustworthy and the releases repeatable. It does
**not** make them self-updating — but it produces everything spec 2 needs, so
that adding the updater is a code change and not a repackaging.

**No public announcement until spec 2 ships.** Anyone who installs a build
without the updater is stranded on it.

## Decisions already taken

| Decision | Choice |
| --- | --- |
| Tooling | Stay on electron-builder; electron-updater arrives in spec 2 |
| macOS signing | Developer ID + hardened runtime + notarization, stapled |
| Windows signing | Unsigned for now; the signer is an empty config slot |
| Hosting | Releases of the public mirror, `simonflore/opennord` |
| Bundle ID | `org.opennord.app` on both platforms (was `app.gigmeister.opennord`) |
| Where releases are cut | This Mac, by one local command. No release workflow in CI |

Electron keys `userData` on the product name (`OpenNord`), not the bundle ID, so
the rename does not move testers' settings.

## Artifacts

Asset names are stable across versions so the website can link to
`releases/latest/download/<name>` and never pin a tag again.

| Platform | Asset | Notes |
| --- | --- | --- |
| macOS | `OpenNord-mac.dmg` | Universal (arm64 + x64). What people download |
| macOS | `OpenNord-mac.zip` | Same app. Unused until spec 2: the updater reads the zip |
| macOS | `latest-mac.yml` | Update feed, generated by electron-builder |
| Windows | `OpenNord-win-x64.exe` | NSIS, per-user install, no admin prompt, unsigned |
| Windows | `latest.yml` | Update feed, generated by electron-builder |

**Universal, with a fallback.** node-usb ships a `darwin-x64+arm64` prebuild, so
a universal app should merge cleanly. If the merge fights the native binary, ship
separate `arm64` and `x64` dmg/zip pairs instead; the asset table grows by two
rows and nothing else in this spec changes. Decide during implementation, on
evidence from the first pack.

**Windows stays x64.** The existing `--x64` pin and its reasoning stand.

## Versioning

- `packages/core/package.json` `version` is the single source. First release:
  `0.1.0`.
- A release is the git tag `desktop-v<version>` on the monorepo commit it was
  built from.
- The release command refuses to run unless the tag exists, points at `HEAD`,
  and matches `version`.
- The beta build number (`build-info.ts`, commit count) is unchanged and still
  shown in-app; `version` is what the OS and the updater see.

The dated-tag convention in `electron/README.md` ("give a startup-fix build a
fresh name") is retired: a real version bump does the same job.

## Build configuration (`package.json` `build`)

- `appId`: `org.opennord.app`.
- `mac`: targets `dmg` and `zip`, arch `universal`, `hardenedRuntime: true`,
  `notarize` enabled, entitlements file, `category` unchanged. `identity: null`
  is removed so electron-builder picks the Developer ID certificate from the
  keychain.
- `win`: target `nsis`. `nsis`: `oneClick: true`, `perMachine: false`.
- `artifactName` per platform, producing the names above.
- `publish`: GitHub provider, `owner: simonflore`, `repo: opennord`. In this
  spec it only makes electron-builder emit the `latest*.yml` files; the pack is
  always run with `--publish never` and the upload is done by the release
  command.
- `files`, `npmRebuild: false` and the node-usb exclusion are untouched.

**Entitlements** (`electron/entitlements.mac.plist`): `com.apple.security.cs.allow-jit`
only, the minimum Electron needs under the hardened runtime. The app is not
App-Sandboxed, so libusb needs no USB entitlement. If the notarized app fails to
load `usb_bindings.node`, add `com.apple.security.cs.disable-library-validation`
and record why — do not add it pre-emptively.

## The node-usb guard

No code change. `scripts/usb-native-guard.mjs verify --target darwin-x64+arm64`
already asserts a prebuild covering both mac arches, and `packedApps` already
finds `release/win-unpacked`. Only the calling scripts change.

`clean` keeps emptying `release/`, so packing one target still discards the
other's output. That is fine: the two platforms are never packed in one run.

## Windows: built in CI, attached locally

A Windows installer cannot be built on this Mac — electron-builder shells out to
wine to stamp the `.exe`, and its bundled wine aborts on current macOS (see
`electron/README.md`).

So `.github/workflows/desktop-win.yml` keeps its job and its triggers, with three
changes:

1. `electron:pack:win` produces the NSIS installer instead of a zip.
2. The uploaded artifact contains `OpenNord-win-x64.exe`, its `.blockmap`, and
   `latest.yml`.
3. A push of a `desktop-v*` tag is added as a trigger, so tagging a release
   produces the Windows half without a manual dispatch.

The workflow still only uploads a workflow artifact. It gets no release
permissions and no new secrets.

## The release command

`npm run release:desktop` (in `packages/core`), implemented as
`scripts/release-desktop.mjs`. Steps, each fatal on failure:

1. **Preflight.** Clean working tree; tag `desktop-v<version>` exists at `HEAD`;
   `gh` is authenticated; a Developer ID Application identity is in the keychain;
   the `notarytool` keychain profile exists; `xcrun notarytool` resolves (full
   Xcode selected, not the Command Line Tools).
2. **Pack macOS.** Guard clean → web build → main/preload bundle →
   `electron-builder --mac --universal --publish never` (signs, notarizes,
   staples) → guard verify.
3. **Verify macOS.** `codesign --verify --deep --strict` on the app,
   `spctl --assess --type execute` on the app, `xcrun stapler validate` on the
   app (electron-builder staples the app, then wraps it in an unsigned dmg).
4. **Fetch Windows.** Find the `desktop-win.yml` run for `HEAD`'s commit; if it
   is absent, still running, or failed, stop and say which. Download its
   artifact.
5. **Draft release.** Create (or reuse) a **draft** release `desktop-v<version>`
   on `simonflore/opennord` and upload all five assets plus blockmaps.
6. **Print** the draft's URL. Publishing is a manual click.

`--mac-only` skips step 4 and uploads no Windows assets, for a macOS-only fix.
There is no Windows-only mode: without the macOS feed file a release would
strand Mac users once spec 2 ships.

Nothing secret is stored in the repo or in CI. The certificate lives in the
login keychain and the notarization credential in a `notarytool` keychain
profile created once by hand.

## One-time setup on the release Mac

Documented in `electron/README.md`, not automated:

- `sudo xcode-select -s /Applications/Xcode.app` — notarization and stapling need
  the full Xcode.
- Install a **Developer ID Application** certificate in the login keychain.
- `xcrun notarytool store-credentials` to create the keychain profile.
- A Node version on which `vite build` runs. Node 26 has broken Vite on this
  machine before; confirm at the start of implementation and, if it still does,
  pin the release command to a working version via `.nvmrc`.

## Website

`src/components/home/DesktopApp.tsx` drops `RELEASE_TAG` and `WIN_ASSET`. The
buttons link to `releases/latest/download/OpenNord-win-x64.exe` and
`…/OpenNord-mac.dmg`; the "all downloads" link goes to `releases/latest`. A

published, otherwise the links 404.

## Docs

`electron/README.md` is rewritten where it is now wrong: the Packing section,
the dated-tag advice, and the claim that macOS produces an unsigned directory.
The "Never run electron-rebuild" section stays as is.

## Testing

- **Unit:** the guard's new target logic, and the release command's preflight
  decisions (tag/version match, dirty tree, missing CI run), tested against
  injected `git`/`gh` results with no network.
- **Automated in the release command:** the `codesign`, `spctl` and `stapler`
  checks above.
- **CI:** the Windows job fails if the installer is missing the `win32-x64`
  prebuild.
- **Manual, per release, not automatable here:** install and launch on a clean
  Mac and a clean Windows machine; connect a Nord.

## Out of scope

- Auto-update (spec 2) and everything in spec 3.
- Windows code signing. SmartScreen will warn on first install.
- A CI release workflow, and macOS builds in CI.
- Linux.
- The open Stage 2 / UsbDk hardware validation.

## Risks

- **Universal merge vs. node-usb** — mitigated by the per-arch fallback.
- **Hardened runtime vs. the native module** — mitigated by the documented
  library-validation escape hatch.
- **Bus factor of one machine** — accepted for now. The command's preflight
  doubles as the checklist for setting up a second one.
- **Mirror lag** — the release sits on the public repo while the tag sits on the
  private monorepo. The AGPL source for a release is the mirrored core commit;
  confirm the mirror has caught up before publishing the draft.
